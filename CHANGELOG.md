# Changelog

Notable fixes and changes, most recent first (full history: `git log`). Moved out of the README, which links here.

- **2026-09-28** — First live readings of the two 27 Sep additions. **The fair head-to-head against BKK: ours 23.9s vs BKK's 28.7s on the same stop visits** (17,151 pairs over Sunday and Monday; 95.3% vs 92.8% accurate by the MBTA standard), the first outside benchmark this project wins on equal information. Details in "A fairer comparison". **Long-range predictions live: 48.2s vs 62.2s for keeping the current delay** (−22.5%, 332k graded), matching the offline walk-forward test's 48.2s, so the offline result held up live. The before/after for the stretch-traffic inputs (live since 26 Sep) is still inconclusive. The previous model's every-stop predictions cover only a Friday evening and a Saturday, so matching like-for-like hours needs the new model's next Friday and Saturday.

- **2026-09-27** — **Long-range predictions: 3, 5 and 10 stops ahead, live.** Until now the model only predicted a vehicle's next stop (~1.5 min ahead), while riders mostly care about 5–15 minutes. Two offline probes and then a proper walk-forward test (22 days, each trained only on earlier days) asked what helps several stops ahead. Telling a model *how far* ahead it predicts gains only 5–8%; telling it *what lies on the path* gains far more: how delay typically changes on each stretch ahead (spare time in the timetable, habitual slow spots), what other vehicles experienced on those stretches in the last 15 minutes, and how late the previous bus of the line was at the target stop. Result: **48.2s vs 58.8s** for "keep the current delay" (−18%, better on all 22 days; 78s vs 92s at 12–30 minutes ahead). Gradient-boosted trees beat a linear model here (−1.2s, more the further ahead) — the first place trees win again since 2026-09-23. Now live: for a random quarter of the confirmed stop arrivals, the prediction service also predicts 3, 5 and 10 stops ahead and grades each on arrival (new table `long_range_predictions`; ~50 extra predictions per 30-second cycle, cycle time unchanged at ~0.5–0.8s). The live code reuses the next-stop model's lookups and was checked against the training data on 400 real cases: 399/400 identical — the one difference a vehicle that stood 45 minutes at a stop before an apparent +2,600s "gain", which the live look-back doesn't reach. The check also caught a precision bug on the *training* side (a float time key rounding a vehicle 4.9 ms before the prediction moment to "same time"), fixed before training the live model. `scripts/train_long_range.py` trains it, `scripts/long_range_report.py` reports its live accuracy. The map doesn't show these predictions yet.

- **2026-09-27** — Started a **fair head-to-head against BKK's own predictions.** The existing comparison uses the randomly sampled predictions, a harder population where both sides score worse, so it can't be set next to the 27s scoreboard figure. Now, for a random ~3% of the stop arrivals the every-stop job predicts, the prediction service asks BKK for its prediction for the same next stop within seconds (a separate 10-second loop — the every-stop job itself waits a minute before predicting, which would hand BKK extra knowledge). About 30 extra BKK calls a minute at rush hour, capped. Stored in a new table (`bkk_stop_samples`, nothing existing changed); `scripts/bkk_every_stop_report.py` compares both on identical stop visits, per model version. First results after a day or two.

- **2026-09-27** — "Accurate" now means something external: the **MBTA** (Boston's transit authority) [arrival-prediction standard](https://www.mbta.com/performance-metrics/arrival-prediction-accuracy) — the vehicle arrives within ±1 minute of a prediction made under 3 minutes ahead, with a wider window further out (±1.5–2 min at 3–6 min, and so on). **94.4% of the stretch-traffic model's live predictions are accurate by it, vs 88.9% for "no model"** (the delay at the previous stop carried forward), over 67k graded predictions from its first ~9 hours (Saturday evening and night). The map's Accuracy colours follow it: green within 30s, light green accurate by the standard, orange/red outside it — the old fixed yellow "30s–1 min off" band had flagged ~19% of vehicles that were in fact accurate. The scoreboard shows both shares.

- **2026-09-26** — Removed an unused database index (vehicle ID on the positions table: 1.2 GB, used 30 times ever) — frees disk and makes each of the ~5,000 inserts a minute a little cheaper. The other four indexes on that table are in active use. No new index for now: the extra per-click lookups take ~0.14–0.23 s, a whole click ~0.5 s.

- **2026-09-26** — The map's **"Live model accuracy" panel now shows the deployed model's real live accuracy**: every vehicle's next stop, graded on arrival (the `stop_predictions` job) — average error, share within a minute, and the error without a model (the current delay carried forward) as a yardstick, plus a line per vehicle type. First reading for the stretch-traffic model: **23s, 94% within a minute, vs 31s without the model**. The panel previously averaged the clicked and randomly sampled predictions of *every* model since early September — a harder, length-biased sample (see the entry below) — and showed ~52s; that version is still available as `/scoreboard/sampled` on the prediction service. Also 4 s → 0.2 s per refresh (and cached for a minute), since it no longer joins the 186M-row positions table. Periods with known bad timestamps are left out: one found on 26 Sep 16:26–16:58, when the ingestion queue fell behind and positions were saved up to ~19 minutes late (a scan of the whole month found no other episode; the training data predates it).

- **2026-09-26** — New model inputs: **recent traffic on the stretch into the stop.** Errors clustered at congestion hotspots (near Keleti ~51s vs ~25s elsewhere), where delay changes fast between stops and the model mostly carries the current delay forward. The new inputs: how much delay vehicles of *any* line gained on the same stop-to-stop stretch in the 15 minutes before the prediction moment (average gain and how many vehicles). Offline, same 22 days: 30.51s → **29.85s** (−0.66s, 95% interval −0.70 to −0.61); worst 10% of errors 61.1s → 59.6s. Live lookup checked against the training data on 400 real stop visits: identical in 400/400 — a check that also caught two bugs before deploy (snapshots without a trip crashed the lookup; a missing upper time bound made lookups for past moments take ~30s). Deployed 18:14; ~70% of live predictions have stretch data (72–74% in training), click and background job give identical predictions, a click takes ~0.5s in total. Also fixed the training script running out of memory at 11M rows (it built all 26 validation folds up front; now one at a time).

- **2026-09-26** — Answered the project's longest-standing question: why live error (~50s) was so much higher than offline (~31s). With every vehicle's next stop now predicted and graded (see 2026-09-25), live accuracy measured the same way as offline is **27.5s vs 28.4s offline** — the model does not degrade live. The scoreboard's sampled predictions (52.8s in the same hours) differ in population: 5% cold starts (232s), 21% made when the last confirmed stop was 2+ stops back (64s), and the rest picked at random moments while driving, which over-represents vehicles on slow stretches (their targets score 32s vs 24s in the every-stop data — an inspection paradox). For identical targets both paths gave identical predictions.

- **2026-09-25** — Vehicle popup reorganised by stop. It showed three numbers from three sources (prediction for the next stop, last confirmed delay at an earlier stop, and how far off a graded prediction was) without saying which stop each belonged to, which read as contradictory. Now: **Next stop** (name + our prediction) and **Last stop** (name, what actually happened, and what we had predicted for it). The last-stop part comes from the same data as the marker colour, so popup and colour can't disagree. When nothing has been graded yet (typically a trip that just left its first stop, which is never predicted) the popup says so, explaining a grey Accuracy marker.

- **2026-09-25** — The timetable now updates itself. `bkk-delay-service/scripts/update_gtfs.py` runs daily at 04:30 (Windows Task Scheduler) and only acts when BKK has published a new version: it checks the new file (complete, not expired, and it must recognise at least as many live BKK trips as the current one), keeps the trips that drop out of it in `retired_stop_times.csv.gz` so past days stay resolvable, installs it, restarts both services, and rolls back automatically if the prediction service doesn't come back healthy. One retired-trips file instead of one folder per old version keeps service startup time flat as updates accumulate. Tested end to end in a sandbox (an 11-Sep → 25-Sep update: live trips recognised 91.0% → 97.1%) and with a forced rollback. Log: `bkk-backend/gtfs-data/update_log.txt`.

- **2026-09-25** — Timetable updated, and older timetables are now kept alongside it. The imported BKK timetable was from 11 Sep; BKK changed parts of it around 18–20 Sep (new trips on lines such as 85, 70, 990, 133E, plus replacement services), so the share of live BKK trips it recognised fell from 96–97% to 91–92% — those vehicles got no prediction, no training label and no map colour. Updated to BKK's 25 Sep feed (97.1% recognised). The newest timetable now wins, and older ones fill in only trips it lacks (the 161,094 trips present in both had identical times). Live: unrecognised BKK trips on the map 100 → 36.
- **2026-09-25** — The vehicle popup now explains the Accuracy colour: "Last graded prediction: off by 53s (we predicted 53s more delay than happened, 8 min ago)". The colour refers to an *earlier* stop than the popup's "Predicted delay", which caused confusion.

- **2026-09-25** — **Every vehicle's next stop is now predicted and graded**, and the map got a **Delay / Accuracy** switch in its legend. Until now live accuracy came only from map clicks plus 50 random vehicles every 5 minutes (~6% of vehicles had a graded prediction at any time). A background job in the delay service now, every 30 seconds, takes each stop visit just confirmed, predicts the vehicle's *next* stop from exactly what was known at that moment, and grades it when the vehicle arrives (new `stop_predictions` table; nothing existing changed). That is the offline walk-forward setup, live and for every vehicle — an unbiased live accuracy figure — and it colours the map by how far off our last prediction for each vehicle was (within 30s / 1 min / 2 min / more). ~250 predictions per 30 s, each cycle under ~1 s; the job, the per-click path and the training data were checked to use identical inputs (200/200 re-derived predictions). A graded prediction for 62% of map vehicles within minutes of starting.

- **2026-09-25** — Vehicles waiting at their first stop no longer show as "early" (blue). Since first stops are measured by departure, the marker used the last sighting there — but while a bus is still waiting, that's just "now", so a bus due to leave at 18:50 showed −102s at 18:48. While a vehicle is still standing at its first stop (seen within the last minute), the color now shows the delay so far: on time until the scheduled departure, late once that has passed. Right after the fix, 99 vehicles were waiting at first stops: 80 on time, the rest late, none falsely early. Map color only; the model and training data are unaffected (they only use departures that already happened).

- **2026-09-24** — New model inputs: **the vehicle ahead** — the previous vehicle of the same line at the same stop (stops are per direction): its delay there, how long ago it passed, and the timetable gap between the two trips. Counted only if it passed before this trip's last stop was confirmed, the same moment a live prediction is made, and the live lookup uses that same moment rather than "now" — checked on 400 real stop visits: live values identical to the training data in 400/400. Offline, on the same 20 days: 31.17s → **30.52s** (−0.65s, 95% interval −0.72 to −0.58), better on every day; the worst 10% of errors shrank too (p90 63.1s → 61.1s). Two other Phase 1 ideas were tested and dropped as null results: encoding hour/weekday as categories (±0.02s). Deployed 2026-09-24 16:52; the extra lookup costs ~50 ms at night, ~230 ms at rush hour per prediction. Live check after 26 hours (4,436 predictions), measured against BKK's own error on the same trips: our gap to BKK shrank from 11.1s to **8.8s** overall and narrowed in 5 of 7 time-of-day slots; 82% of our predictions landed within a minute (BKK ~89%). One day and a different weekday, so read it as "nothing broke, likely helps" rather than an exact figure — but the direction matches the offline test. A vehicle ahead was found for 95% of live predictions (93% in training).

- **2026-09-24** — Re-ran the benchmark against BKK's own predictions with the live scoreboard's current rules (it still scored predictions for stops already reached, and first stops by arrival) and split by production model. Previous gradient-boosted model 48.8s vs BKK 34.9s; current linear model 52.5s vs BKK 40.6s on its first ~2,000 comparisons (evening/night, where BKK also did worse). BKK still wins clearly; the old 55.9s vs 44.3s was inflated on both sides.

- **2026-09-24** — Removed the "route's recent delay" feature (how other vehicles on the same line ran in the last 10 minutes). After the first-stop label fix, the controlled ablation showed the linear model is *better* without it (−0.25s, 95% interval entirely below zero, 18 of 20 days), and the retrain agreed (31.5s vs 31.7s). It was also computed differently live than in training (every sighting in a 10-minute window, including vehicles waiting at first stops, vs one row per stop visit) — the top suspect for live error (~52s) sitting far above offline (~31s). Retrained on the same data as the previous model so the live before/after differs by this one input only; one database query less per prediction. Live check ~15 hours later, matched by time of day and measured against BKK's own error on the same trips (which also varies with the hour): our gap to BKK narrowed by roughly 1s (e.g. 13.2s → 12.2s for 14:00–17:00) — the expected direction but within noise, so this mismatch was *not* the main reason live error sits above offline.

- **2026-09-24** — The 10-minute color cutoff is now timetable-aware: a trip's color stays at least 10 minutes, but longer when the timetable says its next stop is far away (until 5 minutes past when the vehicle, running at its current delay, should have reached it). The fixed 10 minutes had greyed real night buses on long stretches. The delay service computes the cutoff per trip (`stale_after_minutes`); the map just applies it. Live night check: out-of-service vehicles still all grey (21/21); in-service vehicles greyed out dropped from 9 to 4–5 — the rest are night buses skipping request stops nobody used, which a next-stop rule can't see.

- **2026-09-24** — Marker colors now expire: a confirmed delay older than 10 minutes shows as grey ("No recent data") instead of keeping its old color. Before, vehicles heading out of service after their last trip (no current stop, still carrying the trip) kept a color from a stop confirmed 10 minutes to ~2 hours earlier — most of the red markers left after the fix below. 10 minutes is well past the normal gap between confirmed stops (median ~1 min, 90% within ~5 min on the live map). Trade-off: at night a few real vehicles on long stretches between stops also go grey until their next confirmed stop (9 of 181 on the first night check, vs 19 genuinely stale).

- **2026-09-23** — Map marker colors no longer inflate for vehicles standing still. The color used the *latest* "stopped at" sighting of a trip, so a vehicle standing at one stop — typically at the end of the line in the evening, still showing its last trip — got one second "later" every second it stood there (e.g. a bus whose last real arrival was +3 min showed red at +61 min). Found by comparing every live marker against its own popup: 111 of 566 fell in a different color bucket. The color now measures the latest stop at its **arrival** (departure at a first stop), the same definition as the training labels. On the live map at the time: red markers 33 → 7. Endpoint still ~300–600 ms per map refresh.

- **2026-09-23** — First stops are now labelled by **departure**, not arrival, and the model was retrained. At a trip's first stop vehicles turn up early and wait, so the first "stopped at" sighting measured when a vehicle arrived to wait (mean −236s, 90% "early"), not when the trip started — found by splitting errors by position in trip: first stops were 5% of rows but ~183s MAE, adding ~9s to the overall error. The label builder now uses the *last* sighting at stop 1 (the timetable needs no change: arrival = departure at every first stop); first-stop labels went to mean +11s, 86% within ±60s, and every other stop's label stayed bit-identical. The live upstream lookup and `/scoreboard` use the same definition (first-stop predictions made before the switch are still scored against the arrival they predicted). Retraining then picked a **linear model** over gradient-boosted trees for the first time: ~32s vs ~36s steady-state MAE. Checked before deploying that this is real, not a glitch: on the same days with the *old* labels GBT wins (43.8s vs 55.7s), with the new labels linear wins (31.6s vs 35.9s) — the old first-stop labels also corrupted stop 2's "own last delay" input (mean −179s → +11s), a non-linearity only the trees could absorb. Previous model kept as a backup.

- **2026-09-23** — `/scoreboard` now excludes predictions made for a stop the vehicle had *already reached*. The auto-sampler only picks vehicles "in transit to" a stop, but BKK's status can flip back to in-transit while the vehicle is still standing there; the real arrival then predates the prediction, so reconciliation could only find a later sighting of the same visit and scored against that instead. Found by independently re-deriving the scoreboard from raw data: the old 66.7s was arithmetically right, but 1,753 of 10,224 rows (17%) were in this state (median 0.5 min after the real arrival), scoring 131s MAE vs. 53s for the rest. Live MAE is now **53.3s** (8,482 predictions). Also a likely part of the offline-vs-live gap: offline labels use a stop's *first* sighting, while these rows were scored against a later one.

- **2026-09-23** — Static frontend files are now served with `Cache-Control: no-cache` (`spring.web.resources.cache.cachecontrol.no-cache`). Found while verifying the fix below: the deployed fix was correct server-side, but the browser kept running its heuristically-cached old `app.js` until a hard refresh. Now the browser revalidates on every load — a cheap `304 Not Modified` when nothing changed, the new file when it did.

- **2026-09-23** — Fixed map markers occasionally showing a delay color that contradicted the vehicle's own popup (seen: red "6+ min" marker, popup saying −9s). The map's bulk `/current-delays` call sent the *first* vehicle's `serviceDate` for every tripId; since BKK reuses tripIds daily, just after midnight — with vehicles from two service days on the map at once — a vehicle could be colored from *yesterday's* run of the same trip. Two other hypotheses (tripId shared by two vehicles; stop-dwell inflating the delay) were tested against the data and ruled out first. Fix is frontend-only: one call per service date, lookups keyed by serviceDate + tripId. Checked live at 01:10 with both service days active: under the old code 66 of 117 new-day vehicles would have been miscolored (e.g. 34s real delay shown as 1317s).

- **2026-09-22** — Broadened `/scoreboard` from `source = 'click'` only to `source IN ('click', 'auto')`, expecting the larger, less click-biased sample (9,878 reconciled, up from 398) to close the gap against the offline walk-forward MAE. It didn't — the live MAE moved from 63.2s to 66.5s, the wrong direction. Root-caused rather than left unexplained: the ~10% of reconciled rows where BKK also had no comparable prediction score 155.2s MAE versus 56.3s for the rest — closely matching the ~153s cold-start MAE found 2026-09-14 on trips with no upstream-delay reading yet, the same hard subgroup corroborated two different ways. So live prediction demand skews toward genuinely harder cases than offline scoring's roughly-even sample; the gap is now partly explained, not closed. Deliberately did *not* filter out the harder subgroup to make the number look better — it reflects real prediction quality across everything actually served.
- **2026-09-22** — Built the BKK-own-prediction benchmark flagged 09-21 as not-yet-built (`bkk-delay-service/scripts/bkk_comparison_report.py`, read-only, reuses `/scoreboard`'s reconciliation logic). Unlike the Google comparison, BKK's `trip-details` prediction is anchored to the exact tripId/date being tracked, so a direct delay comparison is valid. Result on 8,477 reconciled auto-sampled predictions: this model 55.9s MAE vs. BKK's own prediction 44.3s MAE — BKK wins, closer in only 38% of comparisons. See "External validation" above.
- **2026-09-22** — Regenerated the training dataset (9.5M labeled rows, up from 6.7M) and retrained: still gradient-boosted trees, 23 walk-forward folds (up from 15), steady-state MAE 43.9s (from 43.2s on 09-21) — confirms the offline figure is stable as more data accumulates, not an early-data artifact. - **2026-09-21** — Reconciled the README's accuracy claims against a controlled re-run (same frozen data and model, one change at a time, paired bootstrap intervals over validation days). (1) The old "~53s" figure averaged 17 daily walk-forward folds including the two earliest, where the model had trained on only 1–2 days (errors of 145s and 90s); re-scoring those 17 folds reproduces 53.1s, while the 13 folds from 2 Sep give ~43s (the per-route baseline is ~110s either way). (5) Scale updated to the measured 150M snapshots / 38GB. The live scoreboard (~63s over clicked predictions) and the Google comparison (66s, elapsed travel time) use different populations and definitions, so they are not directly comparable to the offline figure; a like-for-like live number will come from the automatic sampling rows.
- **2026-09-21** — Added an automatic sampling job to the delay-service: every 5 minutes it picks up to 50 random vehicles currently heading to a stop (one snapshot per vehicle from the last 2 minutes, skipping any trip/stop/date already predicted) and runs them through the *same* prediction path a map click uses, logging ours plus BKK's own predicted delay with `source = 'auto'`. The live scoreboard counts only `click` rows and was verified unchanged (380 reconciled, 63.28 s). To keep the job and the click endpoint from drifting apart, both now call one shared `run_prediction()`. - **2026-09-21** — Added a `source` column to `prediction_log` (existing rows default to `click`, since they were all real map clicks) and made `/scoreboard` count only `source = 'click'` rows, so a future automatic-sampling job can gather more BKK-comparison data without changing what the live scoreboard means. - **2026-09-21** — Every `/predict/from-vehicle` call now also looks up BKK's *own* predicted arrival for the same trip and stop (FUTÁR `trip-details`, `predictedArrivalTime` minus scheduled `arrivalTime`) and logs it next to ours in two new nullable `prediction_log` columns, so both can later be graded against the same real arrival. BKK publishes no history of its predictions, so this can only be collected going forward. Additive schema change (`ADD COLUMN IF NOT EXISTS`), best-effort with a 2 s timeout — a failed lookup never affects the prediction, and only the error type is logged since request errors can embed the API key. - **2026-09-12** — Added the upstream-delay feature (this trip's own delay at its last observed stop) - the single biggest accuracy win of the project, roughly halving prediction error (101.4s → 57.7s MAE).
- **2026-09-12** — Java's `RestClient` was silently corrupting every POST to the Python sidecar by attempting an HTTP/2 cleartext ("h2c") upgrade that uvicorn doesn't support. Found via uvicorn's own "Unsupported upgrade request" log line; fixed by pinning the request factory to HTTP/1.1.
- **2026-09-12** — Diagnosed a live "prediction unavailable" bug back to a **9-days-expired static GTFS schedule** — live-vs-static trip ID match rate showed a cliff from ~75% to ~25-43% starting exactly Sep 1 (a mid-season schedule swap, not gradual staleness). Re-downloading the current feed doubled the usable labeled dataset (2.6M → 6.1M rows) — the bug had been silently degrading training data too, not just blocking the new feature.
- **2026-09-09** — RabbitMQ container wasn't surviving reboots (no restart policy, unlike Docker Desktop itself which auto-launches at login). Fixed with `docker update --restart unless-stopped`.
- **2026-09-01** — A larger retrain exposed gradient-boosted trees losing to a dumb per-route baseline — root-caused to a single lucky/unlucky chronological train/val split putting a weekend-heavy period in training and a weekday-rush period in validation. Fixed by reworking evaluation to walk-forward validation (expanding window, one fold per day) instead of trusting one split.
- **2026-08-29** — Delay-label outliers (min ≈ -11529s, max ≈ +12837s) traced to BKK reusing a `trip_id` for a real dispatch at a materially different time than the static schedule snapshot said — confirmed by finding 5+ consecutive stops on the same trip all shifted by one consistent offset. Fixed with a bounded `|delay| > 3600s` filter in the training pipeline once the mechanism was confirmed, not guessed.
- **2026-08-28** — BKK's live vehicle-position feed carries more fields than the static GTFS-derived pipeline was capturing (`deviated`, `stale`) — found via a direct field-by-field diff of BKK's raw response against what was stored. Added both once confirmed real and non-redundant.
- **2026-08-28** — Widened the live-vehicle polling radius from 6km to 25km after finding it was badly under-covering the city (622 → 1714 vehicles as radius increased) — also empirically found BKK's undocumented hard cap (`LIMIT_EXCEEDED` somewhere between 25-28km), since it's not published anywhere.
- **2026-08-28** — The original `vehicle_position_snapshots` schema only captured vehicleId/routeId/lat-lon/bearing - no `tripId`, `stopId`, or `status`, discovered by diffing BKK's raw response against what was actually stored. Without `tripId` there was no way to join a sighting back to a scheduled trip, so **no delay could ever have been computed from that data** - the root fix that unblocked all of stage 5.
- **2026-08-26** — Spring AMQP 4.1's `Jackson2JsonMessageConverter` crashed at startup (`NoClassDefFoundError`) because Boot 4.1 moved to Jackson 3, which doesn't have the classic `com.fasterxml.jackson.databind` classes it expects. Fixed by switching to the Jackson-3-native `JacksonJsonMessageConverter` spring-amqp ships alongside it.
- **2026-08-25** — The live map's vehicle-type coloring was silently broken: BKK's real-time feed reports `vehicleRouteType` as a descriptive string (`"TRAM"`, `"BUS"`) while the static GTFS feed uses numeric `route_type` codes (`"0"`, `"3"`) — found by curling the live endpoint directly rather than assuming they'd match.
- **2026-08-24** — Discovered the real-time API's `stopId` uses `BKK_` + the static feed's `stopCode` field, not `BKK_` + `stopId` — a real mismatch between the static and real-time ID schemes, found by trial and error against the live API.
- **2026-08-24** — Spring Boot 4.1 pulls in Jackson 3, which renamed its packages (`com.fasterxml.jackson.*` → `tools.jackson.*`) and split `RestClient` auto-configuration into its own opt-in starter — both newer than general training-data knowledge, diagnosed from actual error messages and `mvn dependency:tree`.
- **2026-08-24** — Externalized the hardcoded Postgres password to an environment variable (with a local-dev fallback) before the first public push, rather than shipping a plaintext credential to a public GitHub repo.
